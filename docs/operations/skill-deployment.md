# Skill Deployment & Propagation

## How skills propagate

This repository is a **skill-sync consumer** of two sources:

- `product` (`skill-sync` operator skill) — `https://github.com/joeharris76/skill-sync.git`
- `catalog` (`skill-sync-skills`) — `https://github.com/joeharris76/skill-sync-skills.git`

Refs are pinned in `skill-sync.yaml` and the resolved integrity manifest is
`skill-sync.lock`. The local install targets are:

- `.claude/skills`, `.codex/skills`, `.gemini/skills` — all `tracked: true`,
  `install_mode: mirror`.

### Scoped in-repo copies (the deployment model)

Tracked targets are **committed snapshots** (`mirror` + `tracked: true`):
`.claude/skills/**`, `.codex/skills/**`, `.gemini/skills/**` are generated
materializations, byte-for-byte verified against `skill-sync.lock` + the
per-target `skill-sync.config.yaml`. They are the source of truth for
environments that clone only this repo (web agents, CI, fresh machines) where
nothing exists under the author's home directory.

The managed block in `.gitattributes` is `-text` (no EOL normalization) so
hashes are stable across platforms, and the managed block in `.gitignore` is
only the loader-reserved path `.system/` inside each tracked target.

### Consistency invariant

After any skill change, the following must stay in sync in the **same commit**:

1. `skill-sync.yaml` refs/pins
2. `skill-sync.lock` (regenerated by `skill-sync sync`)
3. The three committed target trees + `.gitattributes` / per-target config

CI enforces this with `skill-sync verify` (offline gate, no source access):
it proves the committed snapshot matches the lock; `sync --dry-run` is the
freshness gate that requires source access. The product enforces
same-commit lock discipline via hook scaffolding
(`git_hooks` in the global store); once installed, a commit that touches the
manifest or lock without matching tracked snapshots is refused.

### Updating skills

```sh
npx skill-sync sync --dry-run   # preview
npx skill-sync sync             # apply + regenerate lock
npx skill-sync verify           # offline CI gate
npx skill-sync doctor           # diagnostics
git add skill-sync.yaml skill-sync.lock .claude/skills .codex/skills .gemini/skills .gitattributes .gitignore
```

Prefer advancing `skill-sync.yaml` refs to a merged, published revision on
`main` of each source. Avoid consuming branches directly: the **global loader
store** that serves web/remote agents must be built from merged, pinned
revisions, not an authoring checkout. Feature-branch testing should use
project-local targets sourced from that branch's worktree so the global store
never trails a local experiment.

### BenchBox fork note

BenchBox (`~/Developer/BenchBox`) is a sibling consumer with its own
`skill-sync.yaml` / lock. It maintains its own pin separately (currently at a
derived catalog ref). Updating todo-db pins does not automatically advance the
BenchBox fork; coordinate explicitly and keep shared skills (those without a
vendored fork) at compatible revisions. The historical "todo-db 0.2.0" pin in
that fork predates standalone extraction and is not authoritative for this
repo's current deployment.
